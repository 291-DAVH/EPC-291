# Changelog

All notable changes. Format: Keep a Changelog; versions follow `docs/BRANCHING.md` (releases are tagged on `main`).

## [Unreleased]

### Added
- Several boards per project (Ingeniería › Unifilar): each board has its own data, calculation, memo, summary and diagrams; a board can be added at any time and declares which upstream board and circuit feeds it. Projects with the previous single board are migrated automatically.
- Calculation memo (MC) and project summary (SP) of every board, calculated before the diagram and issued as Markdown (view) and PDF (deliverable): acometida, internal wiring (thermal) vs outgoing wiring (voltage drop, with transition terminal flag), protections (curve, breaking capacity, minimum short-circuit current, overload coordination), residual-current device analysis, trip-curve bands and selectivity between protections in series. The diagram is generated only from a memo calculated on the current data.
- `aea-calc` 1.7.0 (`board_memo`), `board-design` 0.2.0 and patch bumps of the plugins that wrap the engine.

### Changed
- Engineering › Files shows calculations as a readable table (circuits, criteria, compliance) and Markdown as formatted text; the software's own formats (JSON, YAML, Python, Markdown download) are no longer shown to people (technical files only on request, administration).

## [0.3.0] - 2026-10-24
Third release: accounts and organizations with real sign-in (email, alias and Google, GitHub, Facebook, LinkedIn), roles and permissions, inspectors and auditors, master data, issuing to the client, criteria-driven calculation and multi-line diagrams, automatic analysis of customer input, management reports and registers of the methodology, norm review, and a single source of truth per datum.

### Fixed
- **Registers and Reports showed "could not connect to the API (409)" in some demo projects.** The demo generator gave projects a random methodology that included PMI, which does not exist yet (only PM² has a pack; a real project cannot be created with PMI), so their registers and report catalog were missing. The generator now uses PM² only, the 11 demo projects that had PMI were corrected, and a methodology without registers or reports is now reported as such (`available: false`, with a clear message on the screen) instead of failing.

### Added
- **Development MASTER account and account reset (ADR-0015).** A fixed account of the engineering team for development machines: `master` with the password set by `EPC_DEV_MASTER_PASSWORD` in the developer's own, git-ignored `local/dev.ps1` (the repository carries no credential; a new gate check `dev-credentials` fails if one is ever versioned), active only when `EPC_ENV=dev`, loopback only, hidden from every list, the audit log and the staff count, and impossible to register (`@dev.invalid` is reserved). New command `reset-accounts --yes [--audit]` (and `.\local\dev.ps1 reset-users`, with confirmation) that deletes every account, organization, session, invitation, assignment and linked identity (refused in production; projects on disk are kept). In development the sign-in screen now also shows the providers that have no keys yet (Google, GitHub, Facebook, LinkedIn) as disabled buttons marked *sin configurar*, so they can be seen before the keys exist; in production only configured providers are shown. `local/dev.ps1` loads the provider keys from `local/oauth.env`.
- **One expert account for the engineering team.** A single `staff` account now reaches every area without changing user: customer application (all projects of all organizations), technical console, norm review (new *Normas* entry in the customer application too), accounts, assignments, audit log, registers, reports, observations. It can also **work inside any organization** from the organization selector of the sidebar ("Toda la plataforma" by default): while inside one, the people and invitations page of that organization is available (it acts as its owner) and a project created from the application belongs to it. Both applications show a link to the other. Entering and leaving an organization, and everything done there, is recorded in the audit log under the staff member's own name. No other kind of account can do this. New `EPC_CONSOLE_URL` for the console link.
- **Sign in with an alias, and with Google, GitHub, Facebook and LinkedIn (ADR-0014, migration `0004`).** The sign-in form takes one box: email **or** username/alias (optional, chosen at sign-up, in the account page or by an invitation; unique, case-insensitive, no `@`). A provider button appears for each provider configured on the server (`EPC_OAUTH_<PROVIDER>_CLIENT_ID` / `_CLIENT_SECRET`, `EPC_SECRET_KEY`; step by step in `docs/oauth-providers.md`) and the same button signs in and registers: a new person picks independent or company and is created without a password (they can set one later); an invitation can be accepted with a provider that vouches for the invited email. Safety: OAuth code flow with PKCE and a signed state cookie; customer accounts only (staff, reviewers, inspectors and auditors always use their password); an existing account is linked automatically only when the provider vouches for the email (Facebook never does: link from *Account* after signing in); a provider account belongs to one person; the last way to sign in cannot be removed; everything goes to the audit log. Account page: alias, linked accounts and a password section that needs no current password for accounts created through a provider. Tested with simulated providers (no network); it has not been tried against the real services yet.
- **Account types, permission matrix, audit log, inspectors and auditors (ADR-0013, migration `0003`).** `/api/me` now reports eight kinds of account (`staff`, `reviewer`, `inspector`, `auditor`, `individual`, `corporate_owner`, `corporate_admin`, `corporate_member`) and the `abilities` of each; what each kind may do is one table (`identity/permissions.py`) enforced by the request guard, with a test that runs every kind against the same requests. New **company administrator** role (manages members and invitations, never an owner). New **inspector** and **external auditor** accounts, created by staff with the console, that see only the organizations assigned to them (`PUT /api/identity/users/{id}/assignments`, effective at once); the auditor is read-only. **Observations** (`/api/app/projects/{id}/observations`, a register of the methodology): inspectors, auditors and staff record them, the customer's owner or administrators answer, the recorder closes; new project tab *Observaciones*. Platform **audit log** (`GET /api/identity/audit`, console panel *Auditoría de la plataforma*): sign-ins, failed sign-ins, accounts, roles, invitations, assignments, password changes, organization switches and observations, never secrets. HTTP security headers on every response. Read-only accounts no longer see the buttons they cannot use (new project, send information, answer questions). A role change no longer ends the person's session (the role is read on every request).
- **One sign-in for every kind of account.** The person types only email and password; the system works out the type of account and `/api/me` says it (`account_type`): `staff` (engineering team), `reviewer` (norm reviewer), `individual` (independent user), `corporate_admin` (owner of a company subscription) or `corporate_member` (belongs to a corporation), plus the page where that account starts (`landing`: reviewers go straight to *Normas*, the others to their projects). The sidebar shows the type of account. A person who belongs to several organizations sees a selector and changes the active one without signing in again (`POST /api/auth/switch-org`; suspended organizations are not offered). A customer who opens the technical console is sent to the customer application.
- **One source of truth per datum.** New gate check `single-source` (`tools/ci/check_single_source.py`): it fails when two versioned files have the same content (test fixtures and three justified cases are exempt). First clean-up: the drawing engine no longer keeps a hand-written copy of the base design criteria (`BASE_CRITERIA` removed; `catalog_defaults()` reads `engine/jurisdictions/AR/electrical/design-criteria.json`, and a built plugin carries a copy *generated* from it through the new `engine_data` field of the plugin manifest, which also enters the plugin's hash so a corrected norm value marks the plugin as changed); the unused second library of multi-line symbols (`mld/data/mld-lv`, 78 files) and five copies of the same logo and one of the example workbook were deleted. The norm review screen now lives once in `@epc/ui` and is shown by the console and by the customer app for the reviewer role (it was only in the console).
- **Norm review (new module `norms`, new role `standards`):** a dedicated *norm reviewer* account that sees only the review of the norm data (the console shows just *Normas*; it reaches no projects, customers or technical console). By standard and edition the reviewer sees every point (177 rules, 29 calculation tables and constants, 15 base design criteria) and can **correct** it (rules: topic, text, type, parameters, scope, source; criteria: names, default, options, limits; tables: values only, never keys or sizes) and **approve** or **flag** it with a note. Corrections are written into the engine's data files with their own formatting; approvals (who, when, note, fingerprint of the value) go to `engine/jurisdictions/AR/review.json` and every action to `review-log.jsonl`; a corrected point returns to pending and a value changed after approval is *stale*. The criteria catalog is `validated` only when all 15 are approved, and the design pipeline now reads the catalog values (the engine's fixed copy is only a fallback). Staff create reviewer accounts in the console (*Organizaciones*) or with `create-admin --role standards`. `EPC_ROLE=standards` simulates it in development.
- **Project registers as platform data (new module `registers`, tab *Registros*):** risks (RIE), changes (RFC), issues (INC), decisions (DEC), assumptions (SUP) and stakeholders (STK) are no longer Markdown guides filled in by Claude sessions (a leftover of the previous framework) but validated records defined by the methodology pack (`management/methodologies/pm2/registers.json`: fields, options in Spanish and English, closing states). Risk level is derived (probability x impact; low <= 2, medium 3 to 16, high >= 20), closing stamps the date, nothing is deleted and every change keeps who, what and when. Endpoints `GET/POST /api/projects/{id}/registers/{kind}` and `PATCH .../{id}` (admin/engineer). The management reports D11 to D15 now read from them instead of parsing tables. The project skeleton drops `change-requests.md`, `issue-log.md`, `assumptions-and-decisions.md` and `stakeholders.md`, its `05-management/README.md` describes this platform's structure, and the D11 to D15 templates and the M8 catalog point to the platform (tabs *Informes* and *Registros*) instead of `90-management` and fixed phrases.
- **Management reports from the methodology (PM²):** the *Informes* tab now generates the reports the methodology asks for. The catalog comes from the methodology pack (`management/methodologies/pm2/reports.json`: D11 status, D12 progress, D13 risks, D14 effort, D15 changes) and each report follows its template of `rules/management-templates.md`, filled with the project's own data: status and milestones, WBS, schedule, backlog estimates, deliverables, requirements (open questions become the *decisions required*) and the PM² registers kept as Markdown tables (`change-requests.md`, `assumptions-and-decisions.md` RIE rows, `issue-log.md`, `stakeholders.md`; the illustrative `EJ-` rows are ignored). Overall and per-dimension status (green/amber/red) comes from stated rules and its trend compares with the previous report of the same type; what the platform does not hold is shown as *n/d* (hours actually worked are not recorded yet, so D14 reports earned hours from progress). Each report is saved as Markdown and PDF under `workspace/05-management/progress|reports/` (`STATUS-01_20261023.md`), stays internal and is published to the client's Reports list on demand (`POST /api/projects/{id}/reporting/{report}/publish`). Spanish and English. New engine exporter `epc_drawing.export.report_pdf`. The skill `create-management-document` remains for the documents that are not generated automatically.
- **Issuing: download package, transmittal document and sending message.** Each transmittal in *Emitir* has *Descargar paquete* (`GET .../issuing/{TR}/package`): a ZIP `<project>_<EMISSION>_<TR>_Rev<NN>.zip` with its files (folder structure kept), the **transmittal document** `TRANSMITTAL_<TR>_Rev<NN>.pdf` (a delivery note: project, client, issuer, emission, revisions, date, table of documents and formats, remarks, totals; no greetings; new engine exporter `epc_drawing.export.transmittal_pdf`) and `INDICE.csv` with SHA-256. *Mensaje de envío* shows the email text (subject and body, formal register: greeting, bulleted list of documents, package and integrity note, request for acknowledgement, closing and signature, in the project's language; templates in `backend/src/epc/modules/issuing/texts.py`) with copy buttons and *Abrir en mi correo*. Transmittals now record each item's discipline.
- **Answer open questions:** in Requirements each open question is clickable (*Responder*); the answer is stored with who answered and when (`POST /api/app/projects/{id}/requirements/{req}/answer`, field `answered_questions`), the question leaves the open list and the requirement becomes *Definido* when none is left. Answered questions are shown with author and date/time.
- **Accounts, organizations and tenant isolation (US-0018, ADR-0009):** real sign-in. `EPC_AUTH=simulated` (development default) keeps the role-from-environment mode; `EPC_AUTH=required` (production default) uses accounts stored in the database (migration `0002_identity`: passwords, platform role, seats, sessions, invitations; existing `admin`/`user` memberships become `owner`/`member`). **Individual** subscriptions (one person) and **corporate** ones (a group of people with `seats`); a customer sees only the projects of their organization (each project records its owner; another organization's project answers 404), the engineering staff see everything and the console. Opaque session tokens stored hashed (HttpOnly cookie or bearer), `scrypt` passwords, throttled sign-in, invitations (single-use link, 7 days, they hold a seat), owner screen *Cuenta* (people, roles, deactivate, invite, password) and console page *Organizaciones* (create organizations, seats, suspend, team accounts, set a temporary password, assign projects to organizations). CLI `python -m epc.modules.identity.cli create-admin` for the first staff account. Sign-up is closed unless `EPC_SIGNUP=open`. The compose stack now runs with accounts. Limits: no email delivery or reset by email, no MFA/SSO (see the ADR).
- **Automatic analysis of customer input (US-0016):** `POST /api/projects/{id}/analysis` (admin/engineer, explicit `confirm`) sends the pending items to the Claude API (text only, money amounts replaced, no attachments; forced `submit_analysis` tool call, model `EPC_ANALYSIS_MODEL`, default `claude-sonnet-5-5`), validates the answer with the plugin's own `intake.py validate` (one retry with the validator's feedback) and stores it with its `apply`, so it is identical to a manual run; nothing is written unless the whole analysis is valid; every call is recorded in `analysis_usage.json` (cost tracking, risk R-006). Web: *Analizar con Claude* in Input data for the admin/engineer. The key `ANTHROPIC_API_KEY` stays on the server (`pip install epc-backend[analysis]`, included in the Docker image). Tested with a fake client (no network).
- **Criteria-driven design (plugin `board-design` 0.1.0):** the project's design criteria now **govern the calculation** and the calculation **feeds the diagrams**. `epc_calc.aea_pipeline.calculate` takes `criterios` (ΔU limits per circuit type, minimum sections, conductor material and insulation with B2 for XLPE, RCD sensitivity) and a `detalle` dict (type, limit, own and accumulated ΔU, Iz, compliance); the SLD generator takes that result (`SLD_CALC_JSON`, `SLD_CALC_DETAIL`, `SLD_LIM_*`) instead of its simplified calculation and prints the limits it was given. New `epc_drawing.board_design` (CLI and module: calculation -> SLD -> MLD, `--project` or `--input/--criteria`), skill `design-board`, and the web table *Cálculo de los circuitos*. The earlier notice that the criteria were not read is gone.
- **Multi-line diagram generator (US-0019, plugin `mld` 0.2.0, no longer pending):** `epc_drawing.mld.mld_generator` expands each line of the board into its conductors (L1 L2 L3 N) with the MLD_LV symbols per pole (10 mm pitch, not scaled), per-phase balancing of single-phase loads, RCCB groups as sub-busbars, PE, external cables, pagination in IRAM sheets (SVG and DXF); web button *Generar multifilar*; `convert-sld-to-mld` documents the automatic path. The plugin `sld` is 0.1.2.
- **Issuing step (Engineering -> Deliverables):** backend module `issuing` and *Emitir* sub-tab. Prepares a transmittal `TR-nnn` with stamped copies of the DXF (`epc_drawing.export.stamp`: client revision, internal revision, transmittal, hash, engine and plugin versions in the drawing header; the master is untouched), the PDF (existing or rendered from the stamped DXF) and workbooks under `deliverables/<emission>/TR-nnn_Rev<NN>/<discipline>/`; registers them as in review and writes `deliverables/transmittals/TR-nnn.json` plus a ledger event; *Confirm sent* turns them into delivered so the customer sees them and the ZIP package includes them. Only formats with `deliver: true` in the policy are issued.
- **Datos (master data):** new area for what does not change between projects, entered once: company profile, clients, people and logos (backend module `masterdata`, files in `EPC_DATA`, web page *Datos* for the admin/engineer role). Saved clients can be picked when creating a project; the SLD titleblock is prefilled from them and the logos reach the drawing (the titleblock glue now also copies PNG logos).
### Changed
- Project tabs reordered: Datos de entrada, Requisitos, Plan, Ingeniería, Entregables, Informes, Resumen (last, but the one that opens by default). The content area is now centered.
- Projects created before accounts have no owner organization and are visible only to the staff until assigned to one (console, *Organizaciones*).
- **Copyright:** the 177 engineering rules of `epc_calc` no longer carry the `cita` field (short literal quotations of AEA 90364); a rule keeps only the reference (standard, edition, clause, page) and its parameters, written in own words. The verification scripts (`build_rules.py`, `reglas_ocr.py`) that embedded those quotations were removed from the repository; both they and the original rules are kept privately in `local/dev-knowledge/extracted/`. New test `test_sin_texto_literal_de_la_norma`. The quotations remain in earlier git history. Concept documented in `docs/explanation/knowledge.md`; the `**/knowledge/` ignore rule was removed.


## [0.2.0] - 2026-10-23
Second release: management, engineering workspace, SLD data entry, deliverable package and the fixes found by running Docker and a clean CI environment.

### Fixed
- **The `knowledge` backend module was never committed:** the `**/knowledge/` ignore rule (meant for study material) also matched `backend/src/epc/modules/knowledge`, so a clean checkout (and v0.1.0 as published) could not import the backend. The module is re-included, the empty `build/` folders of the project skeleton are kept, and a new gate check (`ignored-sources`) fails when a source file is hidden by an ignore rule. Found by running the CI steps in a clean Linux container.
- **Docker:** creating a project failed inside the image (the non-root user cannot rewrite `claude/plugins/registry.json`); a read-only installation now uses the committed registry. Both images build and the compose stack (PostgreSQL 16, Alembic migration, backend, nginx front) runs; project creation and SLD generation with PDF were verified in the container, and the Alembic upgrade/downgrade/upgrade round trip on PostgreSQL passes.

### Changed
- `tools/dev/seed_demo.py` no longer deletes existing demo data: without `--reset` it does nothing; with `--reset` the current folder is moved to `local/projects-demo.bak-<timestamp>` (last two kept) before regenerating, so manual changes are not lost.
- Pre-commit hook: also blocks `.env` files (only `.env.example`) and added lines that look like private keys or GitHub/AWS tokens.
- Historical documents and `tools/migrate` carry a note mapping the old `platform/` paths to the current layout.

### Added
- **Deliverables: PDF and package.** A drawing delivered as DXF now offers its PDF too (same-name file next to it, only formats with `deliver: true` in the policy; SVG is never offered): buttons `.dxf` / `.pdf` per row and `?format=` on the download. New **Download package** button: a ZIP of everything delivered (folder structure kept, `INDICE.csv` with code, revision and SHA-256), named `<project>_Paquete_Rev00.zip`; with several transmittals, one ZIP per issue (`<project>_IFA_TR-001_Rev00.zip`). The revision shown is the one the client sees (`Rev 00`); the internal revision stays in the transmittal. Engine: `epc_drawing.export.pdf` renders a DXF to PDF (ezdxf + matplotlib, white background, page = drawing size); the SLD generation now also produces a PDF per sheet (`drawings/pdf`).
- **SLD data entry:** backend module `sld` and sub-tab *Datos del unifilar* in Engineering (admin/engineer): board, titleblock and circuit table (parent/child, topology, phase, device, cable type) with validation, "load the plugin example", save, and *Generate diagram* which runs the sld generator unchanged in the background and publishes SVG, DXF and calculation JSON into the engineering folders (visible in Files). Titleblock data typed in the form reaches the drawing; no logos are copied. The backend now depends on `epc-drawing`.
- **Design criteria:** sub-tab *Criterios de diseño* inside Engineering (admin/engineer). Catalog of 15 base criteria for AR electrical (`engine/jurisdictions/AR/electrical/design-criteria.json`, not validated against the standards), per-project overrides with origin (client / standard / project), note and change history, reset to base value, and a design criteria report generated in the project language. API under `/api/projects/{id}/engineering/criteria`. The demo seed no longer writes a static criteria document. Calculation and drawing plugins do not read the criteria yet.

## [0.1.0] - 2026-10-23
First release. It gathers the foundation (plugins, rules engine, portal) and the restructuring into backend, frontend, database, infra and management modules.

### Added
- `planning/` area: vision, roadmap, 3 PRDs, 11 epics, 22 stories, sprints, risk register, release notes and templates; `tools/planning/board.py` generates `planning/BOARD.md`.
- `docs/explanation/what-is-epc.md`, `docs/architecture/` (target architecture, structure, migration phases) and ADR-0001 to ADR-0006.
- ADR-0008: CAD stays 2D with ezdxf and shapely; FreeCAD and 3D out of scope. The Rust desktop edition (ADR-0007, EP-012) is **deferred**.
- Planning for the **desktop edition** (Rust/Tauri, cross-platform): ADR-0007 (proposed), EP-012, US-0023 to US-0027, roadmap milestone M5, risk R-009. UI reused from `frontend/`; Python engine kept as a bundled sidecar.
- **Engineering tab:** backend module `engineering` (overview, sandboxed SVG preview, text/table view of CSV, XLSX, Markdown) under the admin-only surface; web **Ingeniería** tab between Plan and Deliverables, visible only to the admin/engineer role (SVG previews with zoom, lists as tables); demo seed generates single-line and multi-line SVG diagrams plus load and cable lists. `.svg` remains internal, never a deliverable.
- **Cleanup:** `platform/` retired. `platform/tools` -> `tools/` (build, dev, hooks, migrate; `check_skill_conflicts.py` into `tools/ci`), `platform/methodologies` -> `management/methodologies`, `platform/core/workflow` -> `management/workflow`, requirements and the virtual environment to the repository root (`.venv`, `.env.demo`, `.env.admin`), build output to `dist/`. A single `.claude/` at the root. Empty `apps/` placeholders and the obsolete `pyproject.toml` removed; the git hook path is now `tools/hooks`.
- **Phase 8, management module:** backend modules `wbs` (EDT with weighted progress roll-up), `schedule` (dates, finish-to-start dependencies, critical path, slack, conflicts, late activities) and `backlog` (internal; BL-nnn items with type, priority, status, estimate, WBS link). JSON schemas `wbs`, `schedule`, `backlog` in `shared/schemas`; empty files in the project skeleton; demo seed generates a consistent plan for the 20 simulated projects (WBS progress equals project progress). Web: read-only **Plan** tab (Gantt with critical path and today marker, WBS tree). Console: **Planning** page (backlog add/move, Gantt, WBS). Customers can read WBS and schedule (`/api/app/...`); writes and the backlog are admin-only. US-0017 done.

### Changed
- **Migration phase 7:** `database/` (Alembic, baseline migration `0001`, SQLite-based migration tests, README on what lives in the database vs project files) and `infra/` (backend and frontend Dockerfiles, nginx, compose with PostgreSQL 16 and an automatic `upgrade head`, `.dockerignore` that keeps `local/` out of images). CI workflow with the gate, a PostgreSQL migration round-trip and image builds; PR template. The gate gained `database` and `infra` checks (20 in total). ADR-0006 accepted.
- **Migration phase 6:** `platform/apps/web` became the `frontend/` npm workspace: `@epc/ui` (API client, i18n, components, theme, shell, shared new-project form), `@epc/web` (customer app, features `portfolio`, `project`, `new-project`) and `@epc/console` (admin app on its own port, features `overview`, `plugins`, `skills`, `rules`, `checker`, `project-files`). Admin pages are no longer part of the customer bundle. New check `tools/ci/check_frontend_boundaries.py`; the gate type-checks and builds both apps.
- **Migration phase 5:** `platform/apps/api` replaced by `backend/` (modular monolith, package `epc`): `core` (config, errors, fsutil) and bounded contexts under `modules/` with `api -> service -> repository -> models` layers and a `public.py` facade each; domain errors mapped to HTTP in `epc.main`. Boundaries enforced by import-linter contracts generated with `tools/ci/gen_importlinter.py` and an AST architecture test; the gate runs both plus the backend tests.
- **Migration phase 2:** private folders moved under a single git-ignored `local/` (`dev-knowledge`, `legacy`, `projects-demo`, `projects`); `platform/schemas` and `platform/i18n` moved to `shared/`; the project skeleton moved to `management/templates/project-skeleton`; code, hook, ignore rules and docs updated.
- **Migration phase 4:** `engine/` created with five Python packages, each with its own `pyproject.toml`, `src/`, `tests/` and README: `epc_calc` (from aea-calc), `epc_rules` (from `platform/core/rules`), `epc_standards` (from standard-ingest), `epc_drawing` (iec-symbols, iram-titleblock, sld, mld) and `epc_documents` (doc-quality, pm2-docs); `platform/jurisdictions` -> `engine/jurisdictions`. Flat scripts became importable packages (sibling imports rewritten, hyphenated modules renamed, subprocess calls use `python -m`), the SLD no longer needs plugin lookup, and plugins became packaging only. A built plugin carries the engine packages it wraps under `lib/` and the plugin hash covers them. Environment-dependent tests are now skipped explicitly; skills use `python -m` commands.
- **Migration phase 3:** `claude/` created. `platform/hub` -> `claude/plugins`, `platform/skills` -> `claude/skills`, `platform/agents` -> `claude/agents`; `claude/marketplace` template plus `epc_build.py marketplace`; plugins are assembled in Claude Code's official layout (with an install line and `dependencies`); agents referenced by plugins are validated and packaged.
- The gate now builds the marketplace and runs `claude plugin validate --strict` on it and on every plugin (12 checks).
- `tools/ci/run_gate.py`: the 10-check test battery run after every phase.
- Repository organization: README, README.es, CHANGELOG, CONTRIBUTING, `.editorconfig`, `.gitattributes`, `.gitignore` and `.env.example` moved from `platform/` to the repository root; all documentation moved from `platform/docs/` to `docs/` (new `docs/README.md` index).
- A single `.gitignore` for the whole repository.
